# Miyu package template

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This is a template repository for writing [Miyu](https://github.com/miyu-agent/miyu) packages. The manifest, the release workflow, the license and the examples are all ready, so you can click the `Use this template` button on GitHub and start writing your package.

## What is in the repository

The template repository is laid out as follows:

```text
├── my-package/                 # the package itself: the folder name is the package id, change it to your id
│   ├── package.toml            # manifest
│   └── scripts/
│       └── my-package-hello.py # a script, which becomes a tool once installed
├── examples/                   # examples you can copy from, not released
│   ├── meeting-notes/          # skill package: skills/meeting-notes/SKILL.md
│   └── lighthouse/             # knowledge base package: kb/lighthouse/kb.toml and two documents
├── .github/workflows/release.yml  # pushing a v* tag packs the package and uploads it to the release
├── LICENSE                     # MIT license, put your own name as the copyright holder
└── .gitignore
```

## How to use it

Going from a new repository to a collected package takes the six steps below.

### 1. Create the repository

On this repository's page, click `Use this template → Create a new repository`. You can name the repository as you like; `miyu-<id>` is a common choice. A repository created from a template is not a fork, so the package source collects it as usual (repositories forked from another one are not collected).

### 2. Pick an id and replace the placeholders

The **id** is the package's name in the package source, and it is what people type to install it (`miyu pkg install <id>`). An id starts with a lowercase letter, uses only lowercase letters, digits, `-` and `_`, and is at most 64 characters long. Pick a short name that says what the package does: it does not need `miyu-` or the kind of package (prefixes such as `scripts-` and `skills-`), and do not start it with `base-` (that prefix is reserved for packages that come with Miyu). Ids in the package source are first come, first served, so before you pick one, run `miyu pkg search <word>` to make sure the id is not taken yet.

These are the places to change (searching the whole repository for `my-package` finds all of them):

1. Rename the folder `my-package/` to your id: `git mv my-package <id>`. **The folder name is the id**, and local packing and installing both go by the folder name.
2. In `.github/workflows/release.yml`, set both `package:` and `folder:` to your id.
3. In `<id>/package.toml`: `name`, `summary`, `author`, `upstream`, `license`.
4. The script `scripts/my-package-hello.py`: the tool is named after the file, so give the file name your id as a prefix to avoid clashing with other packages; if you do not need this example, delete it.
5. The copyright holder in `LICENSE`. If you switch to another license, change `license` in the manifest to match (written as an [SPDX](https://spdx.org/licenses/) expression, such as `MIT`, `Apache-2.0` or `CC-BY-SA-4.0`).

### 3. Write the content

A package can bring the following kinds of content, and it can mix several of them. The kinds that work as soon as their files are in place only need to go into the package folder by convention, with nothing written in the manifest:

| What you want | What to add | Example |
|---|---|---|
| Give the AI a small tool | `scripts/<name>.py` (or another executable) | `my-package/scripts/` |
| Teach the AI a way of doing something | `skills/<name>/SKILL.md` | `examples/meeting-notes/` |
| A set of material for the AI to look up | `kb/<id>/`: `kb.toml` and documents | `examples/lighthouse/` |
| A slash command | `commands/<name>.md` | See the author guides |
| Personas, presets | `personas/<id>/`, `presets/<id>.toml` | See the author guides |
| An MCP server, a long-running extension program, a background page | Write `[[mcp]]`, `[process]`, `[page]` in the manifest | See the author guides |
| A few settings for people to fill in on the settings page | Write `[settings.<name>]` in the manifest; scripts read them from the `MIYU_SETTINGS_JSON` environment variable | See the author guides |
| A model provider | Write `[providers.<id>]` in the manifest | See the author guides |
| A look, the mascot on the terminal UI's home screen | Write `[theme]`, `[mascot]` in the manifest | See the author guides |
| Methods for other packages to call, content for other packages | Write `[export]`, `[content.<package id>]` in the manifest | See the author guides |

To use an example, copy its `skills/` or `kb/` into your package folder. To take a whole example as it is, copy the example folder to the repository root, rename it to your id, and then update `release.yml`.

Tool and skill descriptions (`Description`, `description`) are for the model and are sent with the request on every turn, so write them as short English sentences, at most three per tool. Names and descriptions for people go in separate places (`显示名称`, `描述`, `display_name_zh`, `summary_zh`).

How to write each kind of content is described in the [author guides](https://github.com/miyu-agent/miyu/tree/main/docs/en/dev), including [content that works as files](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/scripts-skills.md) (scripts, skills, command templates, knowledge bases, personas), [the manifest](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/manifest.md), [connecting MCP servers](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/mcp.md) and [writing extensions](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/extensions.md).

### 4. Try it locally

Replace `<id>` in the commands below with your id, then run them from the repository root. Try it in a separate data directory first, so that the Miyu you use every day is not affected: put `MIYU_HOME=/tmp/miyu-try` in front of each command (bash, zsh and fish all accept this; in PowerShell, run `$env:MIYU_HOME = "$env:TEMP\miyu-try"` first).

```sh
MIYU_HOME=/tmp/miyu-try miyu pkg info ./<id>    # checks the manifest by the same rules as installing and lists what it brings, installs nothing; errors name the line
miyu pkg pack ./<id> -o dist                    # packs dist/<id>-<version>.miyu, prints the SHA-256 and the size (does not connect to the core)
MIYU_HOME=/tmp/miyu-try miyu pkg install ./dist/<id>-0.1.0.miyu
MIYU_HOME=/tmp/miyu-try miyu pkg info <id>      # name, version, what it provides, license
MIYU_HOME=/tmp/miyu-try miyu pkg list           # which packages are installed
MIYU_HOME=/tmp/miyu-try miyu check              # when a script or skill has a mistake, says here why it was skipped
MIYU_HOME=/tmp/miyu-try miyu kb list            # with a knowledge base: shows "from <package name>"; try a search with miyu kb search <word>
MIYU_HOME=/tmp/miyu-try miyu core stop          # when you are done, stop the core for this data, then delete /tmp/miyu-try
```

- A script whose first line is a `#!` line does not need execute permission. A script without a `#!` first line needs execute permission on Linux and macOS: run `chmod +x <id>/scripts/<file>`, and Git keeps that permission.
- Installing again after a change is an upgrade. Once a skill is installed, you can see it by typing `$` in the input box of `miyu`; script tools are listed in the presets in the settings, where each one can be switched on or off.
- Packing leaves out these files: `.git`, `.github`, `__pycache__`, `.DS_Store`, `*.pyc`. Everything else goes into the package, so do not keep files you do not want packed in the package folder.

### 5. Release

To release a new version:

1. Bump `version` in the manifest by one, following semantic versioning (semver) (`0.1.0` → `0.1.1`): the package source goes only by the version number, so releasing the same version again does not count as an update.
2. Commit and push, then make a tag: the tag is `v` followed by `version`.

   ```sh
   git tag v0.1.0
   git push origin v0.1.0
   ```

3. `release.yml` calls the official packing template ([miyu-agent/packages](https://github.com/miyu-agent/packages)), which checks the manifest by the same rules Miyu uses when installing a package, packs it into a `.miyu`, and uploads it to the release for this tag. If the tag does not match `version`, the workflow fails right away.
4. If you want to try packing without releasing: run `release` by hand from the repository's `Actions` page, and the package is in the artifacts of that run.

### 6. Get collected as a community package

Add the topic `miyu-package` to the repository (set it with the gear next to `About` on the right of the repository page). The package source collects once a day (around 03:17 UTC). For each repository it looks only at the latest full release (drafts and pre-releases do not count), collects the `.miyu` files in it and marks them as "community": after you release, expect to wait up to a day.

- Ids are first come, first served: the first repository collected under an id keeps that id, and other repositories that use the same id are not collected. Renaming a package means switching to a new id.
- To check whether your package was collected, run `miyu pkg update` and then `miyu pkg search <id>`. If it does not show up, see the summary of the latest `collect` run under `Actions` in the [package source repository](https://github.com/miyu-agent/packages); each repository that was not collected has one line there with the reason.
- Repositories that are forks or archived are not collected. If one `.miyu` file in the release cannot be read, nothing from that repository is collected in that round.

## Common errors

The table below lists common errors and how to fix them:

| What you see | How to fix it |
|---|---|
| The packed file is called `my-package-…` or some other name | The folder name is the id: rename the package folder |
| Cannot pack: the manifest has no version | Write `version = "0.1.0"` in `[package]` |
| `Unknown key: package.license` | The running Miyu is older than the `license` field: update Miyu, or delete the `license` line in the manifest |
| `tag … does not match version …` appears in `Actions` | The tag without the `v` must be the same as `version` in the manifest |
| `package_conflict` | The name of a tool, skill or knowledge base clashes with another installed package: rename it and install again |
| A script or skill does not show up | Run `miyu check`, which says which one was skipped and why |

For other errors, see [Common errors](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/packages.md#common-errors) in the author guides.
